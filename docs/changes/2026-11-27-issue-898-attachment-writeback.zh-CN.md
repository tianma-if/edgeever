# #898 慢速附件回存与重试

[English](2026-11-27-issue-898-attachment-writeback.md) · [Issue #898](https://github.com/tianma-if/edgeever/issues/898)

Windows 桌面端 2.31.2 向 NAS 实例 2.28.0 回存 38 MB 附件时中断。桌面端的一次上传、冲突后的内容核对及确认上传共用 120 秒总时限。服务端提交后若确认失败，桌面端不会进入更新缓存的步骤。后台确认成功后，过期的手动重试还能把本地状态改回待处理。基线为官方 main 的 7c97ef4a，2.31.2 使用相同的回存实现。

## 范围与验收

- 按每次回存的实际网络进度判断超时。上传使用 Electron 报告的已上传字节，冲突确认下载使用实际读到的数据块。请求开始、收到响应头或字节前进时重新开始计算 120 秒无进展时间。等待响应也受该时限约束。继续使用系统代理、现有认证、禁止重定向和账户切换取消。验收覆盖同一附件的快慢上行、中途降速、停止传输、慢速确认下载及超时后的重试。
- 手动重试只重新调度仍有错误或冲突的记录。验证后台成功后点击旧按钮仍显示已回存，实际冲突仍保留两端内容。旧版已误存为待处理的记录，在本地文件与已确认签名一致时恢复为已回存。
- 用同一资源验证服务器已提交但响应丢失的恢复流程，核对确认后离线读取的字节、大小和 SHA-256。沿用原条件写入和账户缓存路径，兼容实例 2.28.0。此次不引入分片上传、数据库迁移或全库缓存校验。

过短的等待会让确认重复失败，过长会延迟串行队列中下一份附件。错误确认还可能让旧内容被当成本机最新版本，因此必须核对快照哈希。可回滚桌面回存代码，已有待回存记录和快照沿用原格式。报告者的 Windows、隧道及 NAS 组合待实机验证。

## 固定带宽估算的限制

首次修复 cee476d8 以 256 KiB/s 估算耗时，38 MiB 得到 304 秒，即使上行 64 KiB/s 始终有进展，也需要约 608 秒。移除该估算后，耗时由当前连接决定。最坏情况是停滞判断错误导致重复传输或阻塞队列。以实际 Electron 上传、独立服务端读回及停滞用例验证；客户端回滚可恢复原传输实现。

## 按实际进度验证

- 桌面主进程每秒读取当前 PUT 的已上传字节数，只有数值增加才刷新停滞计时。能力探测及冲突确认继续走原传输，确认下载按每个非空数据块刷新。上传采样使用公开的 [Electron ClientRequest.getUploadProgress()](https://www.electronjs.org/docs/latest/api/client-request#requestgetuploadprogress)。
- macOS Electron 44.10.2、隔离账户、v2.28.0 自托管 API。将相同的 8 MiB 写入两份附件，由本地 HTTP 代理分别以 512 KiB/s 和 48 KiB/s 读取请求体。服务端从请求开始到返回 200 分别耗时 16.02 秒和 170.69 秒，两者均只上传一次。客户端实际采到 12 次和 28 次上行字节数增长。独立下载及断网重开均得到 SHA-256 `38507661b214c9285cd0665f2237992ebe664ebaa887fea5cd339c5f77528d67`。
- 真实 Electron 请求携带测试 Cookie 和 Bearer，服务器收到完整 multipart；307 跳转未触达目标，账户取消信号能中止已经收到部分响应的请求。对端写入部分 JSON 后停止，客户端约 121 秒后报告超时。
- `bun test ./apps/desktop/src/main/attachment-writeback.test.mjs -t 'transfer deadlines'` 以可控时钟验证 38 MiB 在 256 KiB/s、64 KiB/s、中途从 256 降到 64 KiB/s 时成功；确认下载很慢也能成功，上传或确认下载停止后可自动重试。修正前的对照中，慢上传、中途降速和慢下载均失败。附件定向 67 项通过，桌面主进程 647 项通过、1 项 Windows 专属测试跳过；桌面界面回存、重启恢复、冲突重试及主工程类型检查通过。
- 2.28.0 对响应丢失的确认仍可能传输整份附件。Windows、群晖和用户实际隧道仍缺现场验证。

## 首次修复的验证记录

- 基线复现命令为 `bun test ./apps/desktop/src/main/attachment-writeback.test.mjs -t 'stale retry|transfer deadlines'`。修复前，184 秒上传和慢速确认均得到 `error`，过期点击和重新加载旧状态均得到 `pending`。修复后 5 项通过，包括超时后自动重试。
- macOS Electron 44.10.2 开发客户端使用独立账户目录，连接由 v2.28.0 源码启动的本地 SQLite / 文件存储服务。通过桌面打开入口创建 XLS 副本，测试写入 39,845,888 字节。代理按读取速率将首个 PUT 限速到 184.004 秒，服务端返回 200 后，代理向桌面返回 502。独立下载确认服务端已提交，随后从桌面桥手动重试。
- 旧服务端的确认顺序为原基线 PUT 返回 409、GET 核对字节、条件 PUT 返回 200 并带回服务端元数据。确认过程仍有整文件传输。再次点击旧重试后状态保持 `saved`。切断网络并从同一入口重新打开，副本、服务端文件、磁盘缓存及缓存元数据的 SHA-256 均为 `fe5a8f2d9f08241db4ab59eaf2734187c29e68b48c5b6f2894059b56ae5eb1ba`。
- 附件打开、回存、IPC、缓存及真实 API 集成共 64 项通过。桌面主进程测试 644 项通过，跳过 1 项仅限 Windows 的进程目录锁测试。主工程类型检查、桌面前端与 sidecar 构建通过。现场 184 秒包含哪些环节仍缺少日志，实测覆盖了慢传与丢响应后的旧缓存，不足以判断报告中的每一份旧缓存来自哪次请求。

## 回存恢复复审

在 5e57eaa1 上补验两条错误路径。PUT 已返回响应头时，按原 HTTP 状态决定是否读取正文；409 的正文断流仍应核对远端内容，旧路由的 404 应暂停回存，认证和资源删除错误应保留类别。必须在读取、取消或出错后结束对应的原生请求。恢复旧的待处理记录时，模拟元数据替换一次遇到 EBUSY，解锁后应恢复已确认状态，清除旧错误并避免重传。改动限于桌面客户端，可回滚到原传输和状态处理，服务端与记录格式兼容。

用户已确认将旧下载覆盖新离线缓存的竞争纳入本轮。对同一账户的同一附件，已启动的下载仍向原调用方返回所请求的内容；回存确认后，该下载失去更新磁盘缓存的资格。缓存字节和摘要的写入必须按顺序完成，慢下载不能阻塞回存或触发额外网络传输。验收从桌面打开入口发起旧下载，编辑并等到回存成功，再放行旧响应、断开附件网络并重新打开，核对服务器、离线副本和缓存摘要。回滚客户端可恢复原有写入顺序，磁盘格式保持兼容。最坏后果是离线重开错误版本，或不同附件的缓存写入互相阻塞。

## 缓存竞争和恢复验证

- 通过 Electron 的“外部打开”入口保留服务器返回的旧下载，编辑另一份副本，等服务端读回新版且桌面记录已回存，再放行旧下载。修复前，离线重开取到旧文件。修复后，原下载仍返回旧内容，关闭测试 API 后，直接重开和完全退出再启动 Electron 后重开，均取到新版，旧下载的临时文件也已清理。服务器读回、磁盘缓存、离线副本逐字节相同，缓存记录的长度为 54，SHA-256 为 `baf3a997de091271171a3cdccbf9e46b46ee1af7faee5761b660d47cb6fbc7d6`。复验入口为 `node tests/desktop-attachment-writeback.integration.mjs <证据目录>`。
- 旧缓存补写摘要也可能读到正在替换中的旧文件。现在同一账户和附件的写入按序执行，回存完成时，之前开始读取的操作失去写缓存资格。定向回归验证旧摘要不会覆盖新摘要。旧版待处理记录修复时遇到一次 EBUSY，解锁后能恢复已回存状态，上传次数保持不变。
- macOS Electron 44.10.2 实测 409 正文挂起、旧路由 404、403 断流或挂起、账户取消、成功响应挂起和正常成功，七项均得到预期结果并释放连接。该组把空闲计时加速为 300 毫秒。桌面主进程测试 653 项通过，跳过 1 项仅限 Windows 的目录锁测试。Electron 大文件缓存修复和取消、主工程类型检查及变更文件 lint 通过。
