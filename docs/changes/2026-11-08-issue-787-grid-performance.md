# #787: Table grid performance
## Goal
On #805, switching the 1,950 × 38 fixture back to the full view took about 7.7 seconds, with 6.9 seconds spent in style calculation and layout. View evaluation took about 1 ms. Saving a cell repeatedly prepared full-table AI context while the sidebar was closed. Make large tables interactive without changing normal editing behavior.
## Scope and acceptance
- Reuse TanStack Virtual to render visible and overscan rows, keyed by record ID. Preserve sticky headings, variable row heights, aligned columns, filtered order, scrolling and active input/focus. Switching views makes no request and does not save.
- Do not generate full-table AI context while the sidebar is closed; when open use the working content. Eliminate repeated save snapshots and Markdown generation. Save one version consistently without swallowing edits made during a save or sending an unnecessary save after reverting to the original content.
- Verify behavior and measure in isolation with 80 × 10 and 1,950 × 38 fixtures. Target p95 for opening/switching/cell edit through confirmed save: 200 ms/100 ms/2 s for the daily fixture and 1.5 s/300 ms/3 s for the large fixture, with the existing debounce included. Exercise editing a distant row, reopening, switching views, and toggling AI.
- Keep grid scrolling inside the workspace pane, and retain upload state when a virtual row leaves and re-enters the viewport. Upload completion must not reset another cell’s in-progress draft or steal its focus. A save acknowledges the uploads referenced by its snapshot and retains assets still used by the successor draft.
## Unchanged
Keep #805's v1/v2, form, offline conflict, export and API contracts. Filter and sort the entire table; do not change limits, autosave timing, protocol or storage. Column virtualization is out of scope unless rows alone are shown to miss the target due to visible columns.
## Acceptance evidence
- Isolated Docker and Chrome on macOS, 20 samples per fixture. The p95 for open/switch to full view/save one cell was 62/31/1,465 ms at 80 × 10 and 289/48/2,758 ms at 1,950 × 38. The large filtered view switch was 50 ms at p95, with no API requests observed in either direction and at most 29 mounted rows in the 1600 × 1000 viewport.
- Browser coverage confirmed that editing the last row and scrolling to the top keeps focus and the input, and the save edits only the original record. Changing views with AI closed does not serialize the table; opening the sidebar computes its context once. Shared table tests cover v1 filtering/order and v2 semantics; the API and storage format are unchanged.
- Browser coverage confirms upload state survives scrolling out and back. Upload completion leaves another cell’s draft and focus intact; both cells save correctly. The grid keeps cells keyed by record and field ID without rebuilding an intermediate row model, and measures resized rows in an animation frame to avoid ResizeObserver loops during scrolling or attachment changes. A save acknowledges only the uploads referenced by its snapshot.
- The isolated D1 comparison covered the original #805 against its baseline. Opening the 80 × 10 fixture went from 9 to 10 rows read; a single-cell PATCH went from 37–40 to 38–41 rows read, with writes unchanged at 23–27. Both versions hit `SQLITE_TOOBIG` when creating the 1,950 × 38 fixture. The grid changes do not alter these server paths; D1 near-limit capacity has a separate acceptance gate from local grid performance.
