# Model-level output budgets

[简体中文](2026-11-03-ai-model-output-budgets.zh-CN.md)

Related Issue: #652

## Problem and outcome

The output limits for text generation (4096), tag suggestions (300) and the built-in AI sidebar (2048) were hard-coded. Long rewrites and translations got truncated, and some reasoning models count thinking tokens toward the output budget, which left the small tag-suggestion budget with almost no room for the answer. Users can now set these three budgets per model. The setting is edited on Web / desktop and applies on Web, desktop, Android and iOS. An empty value keeps the previous default.

## Allowed changes and acceptance

1. Migration `0091` adds three nullable integer columns to `ai_models`: `generation_max_output_tokens`, `tag_suggestion_max_output_tokens` and `companion_max_output_tokens`. `NULL` means "use the default". No backfill, and no earlier migration is modified.
2. The default model's credentials and its three budgets come from one SQL query (`resolveDefaultAiModel`), so a default-model switch between two queries can never pair one model's key with another model's budget. `loadDefaultAiModelCredentials` keeps its return shape, so the infographic, video outline, plugin and discovery prepare responses gain no fields.
3. The text generation, tag suggestion and AI sidebar prepare endpoints (both a new turn and continuing after answered questions) read the matching budget. The response shape is unchanged: still `maxOutputTokens: number`. Tag suggestions keep `temperature: 0`.
4. New `PATCH /api/v1/ai/providers/:providerConfigId/models/:modelConfigId`: an omitted field is left unchanged and `null` restores the default. Empty bodies, unknown fields, non-integers and out-of-range values are rejected. It keeps the existing user-session requirement, workspace isolation and demo / read-only restriction, and writes the `workspace.ai_model.update` audit event. Model creation also accepts the three optional fields.
5. Accepted input: 256–131072 for text generation and the AI sidebar, 64–8192 for tag suggestions. These bounds only catch obvious mistakes; they do not describe what a model actually supports.
6. On Web / desktop, each model chip gets an "Output budget" button (shadcn/ui Tooltip, also shown on keyboard focus) that opens a dialog for the three values. Placeholders show the defaults, an empty field means default, and "Reset all to default" is available. Only changed fields are sent. The button is hidden when the server does not return these fields (older instances). The dialog explains that some models count thinking tokens toward the output budget and that a larger budget helps but does not guarantee every reasoning model works, that the sidebar budget is per model call, and that it applies only to the instance AI model, not to desktop local agents (ACP). New strings cover five languages.

## Boundaries, risks and recovery

- Thinking control, `contextWindow` and ACP local agents are out of scope. Video outline, discovery, infographic and plugin output limits are unchanged.
- Every client already sends the `maxOutputTokens` from the prepare response (`packages/client` for Web, desktop and Android; `AiDirectStream.swift` on iOS), and the Web backend fallback (`/api/v1/ai/provider-relay`) forwards the request body the client built. Upgrading the server is therefore enough for existing clients.
- Worst case: a value above what the model or gateway supports makes that scenario return 400 for this model on every platform. Clearing the field recovers. Larger budgets mean longer outputs, higher cost and latency; one sidebar turn may make several calls.
- Rollback: clear the fields; or revert the commit. The new columns do not affect older code (it selects explicit `ai_models` columns), so the migration does not need to be reverted.

## Implementation and acceptance

- Review fix 1: with a larger sidebar budget a reply can exceed the 16,000-character per-turn limit. The client threw, then completed the turn with the over-long text, which the instance rejected, so the turn never closed. Now the client keeps the text that fits, stops the model request, and completes the turn as failed with the dedicated error code `companion_response_too_long`; the sidebar says the text so far was saved. Process text sealed before tool calls is clipped to its 32,000-character limit too. Verified with a 9,000-token budget and a 17,000-character mock model stream: every checkpoint and completion passes the instance's validation, the turn is saved as failed with 16,000 characters, and the model request is stopped. Saving and closing were also verified on the preview instance.
- Review fix 3: character limits alone were not enough. A 16,000-character Chinese reply plus 32,000 characters of Chinese process text encode to about 144 KB of JSON, above the 128 KiB companion request limit, so the instance answered 413 and the turn could stay running. Checkpoint, completion and tool-execution bodies now fit both the field character limits and the UTF-8 byte size of the whole JSON request: the oldest process text is dropped first, and the reply is only shortened if the body still does not fit. The server limit now comes from the same shared constant. An HTTP regression test runs the client code through the real companion routes, including the body limit: every request returns 200, the turn is saved as failed with the whole 16,000-character reply, and the most recent process text is kept; the same test fails on the code before the fix. Re-checked on the preview instance: the raw body still gets 413, and all 54 requests from the fixed client succeed.
- Review fix 2: if settings refreshed while the budget dialog was open, untouched fields were sent as edits and could clear a value another device had just saved. Edits are now judged against a snapshot taken when the dialog opened, and only fields the user changed are sent. The Playwright spec covers "dialog open → another client saves a tag budget of 800 → reconnect triggers a settings refresh → edit only the generation budget and save" and confirms only that field is sent and 800 is kept; the same spec fails on the code before the fix.
- `ai-output-budgets.ts` defines the defaults, input bounds and fallback rule. `ai-service.ts` adds `resolveDefaultAiModel`; `ai-routes.ts` adds the PATCH and wires text generation and tag suggestions; `companion-routes.ts` / `companion-prepare.ts` wire both sidebar prepare paths. Web adds `AiModelOutputBudgetDialog.tsx`, and `packages/client` adds `updateAiModel`. Direct-call, backend-fallback and iOS code are unchanged.
- Automated: new API tests cover defaults, the omitted / `null` PATCH semantics, input validation, workspace isolation, demo and API-token rejection, auditing, credentials and budget staying paired after a default-model switch, unchanged shapes of other prepare responses, and "rows written by the old version → migration → old-version reads and writes". Sidebar tests cover the new-turn and continue paths, plus shared and client unit tests. A new Playwright spec `ai-model-output-budgets.spec.ts` (edit, validation, keyboard-focus tooltip, persistence after reload, reset) runs in the existing browser CI step, with no new runner.
- `bun run test` (rebased on the latest `upstream/main`, which includes #779): 6 of 5393 tests failed, none caused by this change. Four fail because the worktree path contains non-ASCII characters (`模型参数`) and all pass on the same commit from an ASCII path; `deployment-entrypoints` fails on unmodified `upstream/main` too; `stores multiple models under one OpenRouter-style provider` failed once (two models created in the same millisecond are ordered by random ID) and passes when re-run. An existing expectation was updated because the settings response gained three `null` fields. `bun run typecheck`, `bun run typecheck:mobile`, `bun run build:web` and `bun run lint` pass.
- Self-hosted cross-version end to end (the `self-hosted-server` entry used by Docker, one SQLite data directory): the released v2.18.0 client library (its direct-call, fallback and iOS request code is identical to current `main`) against a local mock model service, covering text generation, tag suggestions and the AI sidebar, each both direct and via the backend fallback. All 41 checks passed: the old server sends 4096 / 300 / 2048; after upgrading, existing data still uses the defaults; after PATCH the requests carry 16000 / 800 / 9000; `null` restores the default; after rolling back to the old server, settings load, models can be added and removed, and requests return to the old defaults; upgrading again keeps the values saved before the rollback.
- Upgrade from existing data (re-verified after renumbering the migration to `0091` on the latest `main`, which includes #779): in isolated environments, unmodified `main` was run first (migrated to `0090`), and a regular user, an AI service with two models and a default model were written through the old version's API; then the instance was upgraded to this branch.
  - Self-hosted SQLite (the `self-hosted-server` entry used by Docker, same data directory): only `0091` is applied on start; users and AI configuration (service, models, default model) match the pre-upgrade state and the existing user can sign in; models without a budget still use 4096 / 300 / 2048; new budgets save, apply only to that model, and take effect for text generation, tag suggestions and the sidebar; `null` restores the default.
  - Cloudflare D1 (isolated preview instance: its own Worker, D1, R2, auth secret and preview domain, separate from production): a new D1 was created, unmodified `main` deployed and migrated to `0090`, the same data written, then migrated to `0091` and this branch deployed. The same checks pass over HTTP, `0091` applies, and the user and model counts are unchanged.
- Earlier preview verification (when the migration was numbered `0088`): with the v2.18.0 client library, all three generation paths passed 24 checks both direct and via the Worker backend fallback; after rolling back to unmodified `main`, settings loaded, models could be added and removed and the old defaults returned; upgrading again kept the values saved before the rollback; the settings dialog worked in a browser.
