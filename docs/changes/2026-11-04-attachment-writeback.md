# Issue #771: write back externally edited desktop attachments

[简体中文](2026-11-04-attachment-writeback.zh-CN.md)

## Problem and outcome

[Issue #771](https://github.com/tianma-if/edgeever/issues/771) requests automatic replacement of the original attachment after saving it in an external application such as Excel/WPS, without saving as and uploading again. The baseline is official `main` at `6be20cfc`: desktop opening creates independent local copies; the shared API already supports conditional replacement using `expectedContentHash`. Keep the agreed desktop scope; do not parse or merge Office documents.

This is a high-risk data-writing feature. Its value is completing external editing; the worst outcome is uploading incomplete bytes or overwriting another device's changes. Use complete snapshots, existing hash-based conditional writes and durable pending content. Reverting desktop changes stops new writebacks without a database migration; a code rollback does not restore content already replaced, as the server does not retain attachment versions. Before downgrading, copy unsynced local files elsewhere: older versions do not recognize writeback state and can apply their previous temporary-file cleanup policy. Real Windows Excel/WPS, other desktop platforms and old-to-new upgrade paths require separate acceptance; automated checks and builds do not establish those outcomes.

## Preserve the server filename

Renaming an attachment does not change its content hash, while the previous writeback submits the opening filename and can reverse the cloud rename. A note label differing from the actual filename has the same problem. The original no-server-contract-change boundary is therefore narrowed to allow the backward-compatible S6 extension, without changing existing callers’ filename replacement semantics. Preserve the name atomically in the database update; a client read-before-write cannot provide that guarantee. The optional field alone cannot protect against older servers that ignore it, so desktop writeback first probes support and then uses a dedicated route that always preserves names. Unsupported servers retain edits until an upgrade and manual retry. The dedicated route also protects downgrades between discovery and writing; `X-EdgeEver-Writeback: preserve-filename` distinguishes a supported route’s missing resource from an older server’s missing route.

## Unchanged boundaries

- No server replacement contract changes except the optional S6 field, capability discovery and dedicated writeback route; no authentication changes except S8 session-memory assignment order, and no permission, schema, migration, upload-size or file-type allowlist changes; no installer, auto-update or release changes.
- Do not edit the authoritative attachment cache in place or delete unsaved copies. Historical copies have no trustworthy baseline and must not be uploaded automatically.
- Do not follow Save As to other paths, add Office plugins, collaborative editing, format parsing/merging or attachment version history.
- Preserve browser/mobile links, downloads, note editing and existing offline new-attachment uploads. Do not operate on production instances beyond the specified CF acceptance below, or modify existing user notes.
- Actual Windows Excel/WPS saves, offline recovery, cross-device conflicts and old-to-new upgrades remain platform acceptance items when their environments are unavailable.
