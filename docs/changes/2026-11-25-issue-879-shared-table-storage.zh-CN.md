# #879 多维表格共享记录存储

[原需求](https://github.com/tianma-if/edgeever/issues/879) · 基线 `18720460` · [候选实现](https://github.com/sivdead/edgeever/commit/1558f1e9037fc2f17a4d56ad4819d1625b112769)

## 范围与风险

- 将当前记录由笔记正文迁入 D1 与 Docker SQLite 共用的 JSON 行表，以工作区、表和行序限定查询。单行编辑只更新该行及必要的历史和索引。保留字段、视图、权限、排序语义及已有附件引用。
- 维护窗口先备份并暂停表格写入，涵盖同步和公开表单。一次只推进有限记录，进度与数据同事务写入。校验所有表后切换。切换前可恢复旧正文读写，切换后回退到已验证能读写共享记录的服务版本。
- 客户端按修订上传及拉取变化，含删除。过期提交保留草稿，重复请求返回原结果。既有格式继续可读，历史及默认备份恢复需覆盖迁移前后和跨字段类型的附件引用。
- 最坏后果是漏迁、串表、并发覆盖或回滚丢写入。用本地合成数据及真实旧版生成的 v1/v2 表验证 D1 模拟和同卷 Docker 升级，覆盖中断、校验及回滚。生产切换单独验收。
- 用连续 keyset 翻页、一次性筛选计数、元数据行数和有限已保存视图索引控制读取及索引成本。记录整次分页、同步、当前快照、历史及迁移的累计成本，单列 SQLite 本地指标和 D1 计费口径。迁移前为新旧共存、索引维护和实例其他写入预留额度，额度耗尽保留断点并明确诊断。

## 本地实现与证据

- `0100_shared_table_records.sql` 增加当前记录、修订和迁移状态。`SharedTableMigration` 按笔记 ID 盘点、每次复制最多 25 条记录，记录与断点同事务提交。迁移前和准备完成后仍读取旧正文。维护期间表格正文写入返回 `409 table_migration_in_progress`。
- `SharedTableStore` 独立更新记录，保存字段及视图元数据、删除记录和历史版本。修订条件阻止过期草稿覆盖，重复提交返回已持久化的原回执。按修订及记录 ID 继续拉取变更。现有编辑器的文本排序继续沿用 `localeCompare`，候选 SQL 文本排序尚未接入编辑器。
- `table-storage-migration.integration.test.mjs` 使用 Bun SQLite 和随项目锁定 Wrangler 安装的 Miniflare。验证并发推进、续跑、字段增删与改型、修订冲突、重复提交、删除增量、历史恢复、视图分页和旧格式回写。当前 2,000 行快照一次读取表头、40 次读取数据页，查询总数为 41 次，按行序索引分页，无历史查询或重复计数。此处的查询次数与 [D1 计费读写行数](https://developers.cloudflare.com/d1/platform/pricing/#definitions) 分别记录。
- 真实 `ghcr.io/tianma-if/edgeever:v2.31.2` 旧服务通过 API 创建 v1/v2 表和实际附件。用当前服务 bundle 在同一个测试卷启动并应用 `0100`。在 25 行时退出迁移进程，再启动后累计复制 4 张表、202 行，含 2 张旧版自带的示例表。维护中普通笔记可写，写入表格返回 409。共享存储更新两张测试表并分别删除一行。回滚也分两个进程完成。原镜像在同卷重启后通过 API 读到新值、删除结果、视图、此前历史和附件实际字节。
- 67 项定向测试通过，覆盖上述存储测试和现有表格、公开表单、备份恢复、同步与数据库错误回归。`bun run typecheck`、`bun run typecheck:mobile`、`bun run build:web` 通过。测试使用本地合成数据。

## 回滚边界

- Miniflare 中，1,100 行、每行一个 2,000 字符的合法文本单元格可以存入共享记录。回写旧格式时，Markdown、富文本 JSON 和纯文本合计约 9.7 MB，触发 `SQLITE_TOOBIG`。D1 单行上限为 2 MB，因此切换后的回退版本必须支持共享记录，并使用原卷或原数据库继续读写。[D1 限制](https://developers.cloudflare.com/d1/platform/limits/)

## 正式读写接入

- 已复制并核对的实例通过原子事务切换。迁移前的正文和历史照常可读。切换后的表格正文和历史可引用共享记录修订，既有接口按该修订生成兼容文档。当前改动先验证普通笔记保存、字段变化、公开表单和历史的共用写入路径。
- 普通保存保留编辑会话、笔记修订与资源处理。按记录 ID 对比完整文档，只写变化的记录。记录写入、笔记修订及兼容引用同步提交。列表、分享、同步与备份应读取同一记录来源。新容量及回滚目标在实际启用前验收。
- 最坏情况为旧调用方读到内部引用、跳过新写入或并发覆盖。先以旧版数据和现有接口验证单行更新、并发与历史，再验证各兼容读取入口。切换操作在兼容入口验收完成前仅由本地测试调用。

- `0101_shared_table_memo_references.sql` 增加原子切换状态及当前正文、历史的共享修订引用。编辑会话约束继续沿用；保持切换前最后一份表的状态可恢复。当前记录移除附件时保留仍关联历史的附件。公开表单从元数据读取字段和行数，再追加一行。
- 现有编辑器、分享、普通同步和备份返回兼容文档，可从默认备份恢复当前表及历史。`/api/v1/memos/:id/table/query` 支持按视图分页，`/api/v1/memos/:id/table/changes` 按修订传递变更和删除。两者沿用 `read:memos` 和笔记本访问权限。现有客户端仍使用原同步协议。
- `bun test apps/api/src/table-storage-migration.integration.test.mjs` 覆盖 D1 模拟的迁移、切换与普通单行编辑，及 SQLite 上的表单、兼容同步、备份和历史恢复。使用 `v2.31.2` 真实镜像创建 v1/v2、附件和原公开表单，在同卷以当前服务 bundle 应用 `0101`。迁移 25 行后停止，再启动完成 4 张表共 140 行。切换后通过 HTTP 验证既有编辑会话、旧表单、行修订、视图分页、列表搜索、公开分享、同步和备份，当前表移除附件后仍能读取历史引用及原附件字节。
- `bun test apps/api/src` 通过 1069 项。`bun run typecheck`、`bun run typecheck:mobile`、`bun run build:web` 和本地 `bun run build:self-hosted` 通过。

## 维护窗口操作

1. 用实例所有者会话访问 `GET /api/v1/admin/table-storage`。逐页向同一路径 `POST` `{ "action": "estimate" }`，使用 `estimate.next` 作为下一次请求的 `cursor`。合计 `readRows`、`writeRows` 和 `extraBytes`，从实例和账号当前余量中扣除要留给日常使用的部分。保留能读写共享记录且经验证的回退构建。
2. 在维护窗口备份，核定额度和空间后提交 `{ "action": "start", "backupConfirmed": true }`。表格写入返回 `409 table_migration_in_progress`。提交 `advance`，在 `budget` 中传入本次操作可用的 `readRows`、`writeRows` 和 `extraBytes`，检查 `progress`，逐步推进到 `ready`。预算不足返回 `paused` 并保留断点。D1 日额度耗尽返回 `503 database_daily_quota_exceeded`，可在额度恢复后续跑。
3. 核对表数、行数和代表性样本，提交 `activate` 后确认 `active`。验证旧表、编辑、同步和备份。激活前如需撤回，先提交 `abort`，再逐步 `advance` 到 `legacy`。激活后保留数据库和共享记录，以兼容构建回退。

## 分块备份

- 500 行、10 个长文本字段、6 份历史的样本，单条查询仅记录字段就返回约 60 MB。默认备份以有界请求分块读取当前记录和历史，在每次请求中核对源版本。验证 Web 手动、WebDAV 和桌面默认备份调用共用分块能力。[D1 限制](https://developers.cloudflare.com/d1/platform/limits/) · [Workers 限制](https://developers.cloudflare.com/workers/platform/limits/)
- 保留旧客户端的接口和 v1/v2 ZIP 导入。新档案按记录与历史分条存放，继续提供可读 Markdown 和现有附件流。将表及历史分块暂存，完整性校验通过后在单个事务发布。提交前中断或检测到并发修改，目标表保持原样。大型档案恢复要求目标启用共享存储，沿用实例维护窗口的切换流程。
- 用本地合成数据覆盖超过 D1 单次结果上限的完整档案、重试、取消、并发源修改与恢复期间编辑，核对历史、字段、行序、附件引用及累计 D1 读取。保留生产切换独立验收。

- `0104` 增加分块恢复暂存表和历史分页索引。启用共享存储的服务在备份状态声明分块能力，含共享修订的档案采用 ZIP v3，每块最多 25 行。旧备份接口继续服务原客户端，新客户端仍能读取 ZIP v1/v2。未启用共享存储的源保留普通导出。桌面、Web 手动导出及 WebDAV 迁移共享 ZIP 读写逻辑。
- 分块恢复按单张表发布当前记录和全部历史。重复提交同一块及重复发布可重放，完整性和目标修改检查在发布事务内确认。取消清理暂存分块，后续恢复会分批清理闲置超过 24 小时的任务。附件沿用原有流式传输。

- 真实 Chrome 在两个隔离的 Docker `0104` 实例间通过默认设置界面导出并导入 ZIP v3，复核当前表、历史及附件原始字节。桌面备份 Worker 在 Electron utility process 中完成 ZIP v3 往返，并验证真实 `v2.31.2` 服务器导出的 ZIP v2 可恢复到 `0104`。1,085 项 API 与 ZIP 测试、8 项 Electron 备份网络测试、67 项桌面备份单测、Web 和移动端类型检查、Web/Docker/桌面备份 Worker 构建通过。

### 分块备份复审

- 迁移接受旧格式中已有的超过 2,000 行的表，ZIP v3 应能完整往返。保留每块的大小和数据完整性检查，并用旧格式迁移后的 2,001 行表验证。
