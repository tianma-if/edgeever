# #787：网格性能
## 问题与目标
在 #805 的 1,950 × 38 样表上，切回全量约 7.7 秒，其中约 6.9 秒是样式计算和布局。视图计算约 1 毫秒；改单格保存期间 AI 关闭仍重复生成上下文。让大表可交互，并保持日常表与既有编辑语义。
## 允许的变更与验收
- 复用 TanStack Virtual，仅渲染可见行和缓冲行，按记录 ID 定位；保留吸顶表头、可变行高、整表列对齐、筛选后行顺序、滚动和编辑中的焦点/输入。切换视图不请求服务端、不触发保存。
- AI 关闭时不生成整表上下文；打开后以当前工作内容提供上下文。减少重复保存快照和 Markdown 生成；一次保存使用同一版本，进行中的保存不会吞掉后来编辑，编辑后撤销到原内容仍不发送无效保存。
- 隔离环境使用日常表（80 × 10）和大表（1,950 × 38）核对行为和性能。大表打开/切换/改单格到确认保存的 p95 目标分别为 1.5 秒/300 毫秒/3 秒，日常表分别为 200 毫秒/100 毫秒/2 秒，保存包含现有防抖。验证滚动到远端记录编辑、保存后重开、视图与 AI 开关行为。
- 隔离表格滚动与工作区外层滚动；附件行离开视口再回来时继续显示上传状态；上传回执不能重置另一格正在输入的草稿或夺走焦点。保存完成仅转移本次快照引用的附件，保留后续编辑仍在使用的上传。
## 保持不变
沿用 #805 的 v1/v2、公开表单、离线冲突、导出和 API 契约；筛选排序仍计算全表，不改记录上限、自动保存延时、协议或存储。不做列虚拟化，除非行虚拟化后可见列本身仍被证实阻塞目标。
## 完成核对
- macOS Chrome、隔离 Docker，两个数据集各 20 次。80 × 10 打开/切回全量/改单格保存的 p95 为 62/31/1,465 毫秒；1,950 × 38 为 289/48/2,758 毫秒。大表切到筛选视图 p95 为 50 毫秒，两方向均未捕获 API 请求；1600 × 1000 视口最多挂载 29 行。
- 浏览器验证编辑表尾后滚到顶部仍保持焦点和输入，保存只改原记录；AI 关闭时切换视图不序列化整表，打开时生成一次上下文。共享表格测试覆盖 v1 筛选排序与 v2 语义，API 与存储格式不变。
- 浏览器回归覆盖带附件列的长表：滚出视口再返回仍显示上传中；附件回执到达时，另一格的输入和焦点保留，两格都正确保存。表格按记录和字段 ID 保留单元格，不再重建行模型；行高在动画帧中重测，避免滚动或附件改变行高时触发 ResizeObserver 循环。快照回执只确认本次引用的上传。
- 独立 D1 对照测的是原 #805 与其基线：80 × 10 打开读 9 → 10 行；改单格 PATCH 读 37–40 → 38–41 行，写仍是 23–27 行。两版创建 1,950 × 38 样表均触发 `SQLITE_TOOBIG`。网格优化不改变这些服务端路径；近上限 D1 容量须单独验收，不用本地网格的成绩代替。
