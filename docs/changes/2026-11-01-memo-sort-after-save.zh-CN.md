# 编辑笔记后保持列表排序

[English](2026-11-01-memo-sort-after-save.md) · [Issue #750](https://github.com/tianma-if/edgeever/issues/750)

## 问题与目标

反馈描述 Windows v2.16.1 在笔记本选择标题 A–Z 后，编辑的笔记会跳到首位。桌面查询使用 SQLite `NOCASE`，缓存更新使用中文区域比较；源码级隔离复现已出现仅修改正文就改变不同中文标题顺序的现象。修改产品代码前，先在最新官方桌面版确认实际行为。

## 允许变更与验收

1. 在现有机器通过应用内更新或官方安装包安装最新 macOS 正式版，保留官方安装包作为恢复来源。使用独立应用配置和本地测试实例，不编辑或迁移用户真实笔记。通过安装包的界面复现“标题 A–Z → 修改正文 → 返回”，保留必要的前后证据；Windows 专属验证单独说明。
2. 确认复现后，修复列表更新：仅修改正文时，不改变不同且未改名的标题之间的相对顺序，并保留当前排序选项。实际改名、同名次序、新建笔记和 ID 映射应与该列表的数据仓库排序保持一致。覆盖标题 A–Z、Z–A，保留创建/更新时间排序、筛选、笔记本/标签约束、数量和分页入口。
3. 不增加全库读取、客户端全库排序、正文保存时的额外网络请求、迁移、索引或新依赖。只处理已加载的列表/缓存，或复用现有有界查询。用代表性的缓存列表规模比较保存/更新开销，核对分页边界和查询次数。
4. 实现前扩展现有缓存回归用例，使其能暴露已复现的缺陷。修复后在桌面运行时验证编辑返回、改名和跨页列表；复用相关测试，并对最终候选执行一次 `bun run typecheck`、`bun run typecheck:mobile`、`bun run build:web`。

## 保持不变的边界、风险与恢复

本次恢复已选列表排序，不重新定义语言排序、置顶优先级或无标题笔记的展示。原生 Android/iOS 客户端、存储/认证/同步机制、安装/升级机制、服务端部署、Release 和版本号均不变。分享及备份等无关行为保持不变。

功能价值是编辑后仍能按预期定位笔记。主要风险是缓存顺序与仓库分页不一致，导致位置错误或重复展示；保持查询参数格式和分页入口，并验证已加载页面交界。需要回滚时撤回列表更新代码，不计划迁移数据；需要恢复应用时，可用保留的官方安装包重装 v2.16.1。Windows 等不可用平台仍需各自运行验证。

## 实施决策与完成核对

已安装的官方 v2.16.1 复现了缺陷：仅保存正文后，`中文笔记 → 笔记整理 → 阿尔法` 变成 `阿尔法 → 笔记整理 → 中文笔记`，标题未改动。前后截图见[验收证据](evidence/2026-11-01-memo-sort-after-save/)。

以现有仓库排序为准。桌面标题缓存排序对齐 sidecar 的 SQLite `COALESCE(title, excerpt) COLLATE NOCASE`，再按更新时间和 ID 降序排列。SQLite 只折叠 ASCII 大小写，不替换成语言排序，也不套用与查询不同的去空白或回退规则。浏览器缓存行为和 sidecar 查询保持不变；和原来一样只排序已加载摘要，不增加仓库/网络请求或全库读取。这样无需为渲染缓存不一致而改变索引查询、分页或桌面原生代码。

ID 次序也须使用 SQLite 的 UTF-8 二进制顺序：恢复笔记允许非 ASCII ID，JavaScript 的 UTF-16 顺序可能不同。标题和 ID 共用码点比较实现，分别保留 ASCII 忽略大小写和二进制语义，不改变可接受的输入。桌面标题列表插入未见过的笔记时，应与所有已加载页面一起排序，而非只排序首页。保留既有的首页新增一个位置，使新建/已选笔记仍留在缓存，保留分页参数，并一致更新缓存数量。不丢弃笔记、不主动读取未加载页面，继续使用原有的重叠页去重。

缓存中的标题编辑/插入之后，继续加载的页面不会经过缓存更新辅助函数。展示列表须在已加载、去重的摘要上复用同一个桌面标题排序器，避免续页又把已编辑笔记显示到错误位置。仅改变 `WorkspaceApp` 的桌面标题列表投影，浏览器及其他排序的投影不变；不增加读取，不排序未加载笔记。

“始终保留 offset 游标”的原决定已被真实分页反例替代：已知前缀中的笔记改名后排到末尾，旧 offset 会直接跳过下一条源笔记。仅对桌面标题列表，当标题编辑、回退的更新时间或 ID 映射使前缀成员被移除、去重或移到原前缀边界之后时，向前回退最后一页的 offset。用该 offset 推断保守的已知前缀，避免反复编辑已在前缀外的同一笔记时持续回退。更新时间不回退的普通正文保存、以及仍在前缀内的变化保留游标，其他游标和分页参数不变。下一次正常翻页用有界重叠补齐缺口；不主动发起读取、重试、计数或全库扫描。源记录数恰好落在整页边界时，重叠可能需要额外一页：100 条记录、每页 50 条的回归中，改名前剩余 50 条/1 页，修复后读取 51 条/2 页，只有 1 条重叠；同一前缀外笔记反复改名不会继续增加重叠。

## 完成核对

- 已通过现有应用内更新安装官方 v2.16.1，并在独立 macOS 配置中复现“修改正文 → 左上角返回列表”；原始复现截图和官方恢复安装包继续保留。
- 桌面标题顺序对齐 SQLite `NOCASE` 及 UTF-8 二进制 ID 次序，覆盖恢复笔记的非 ASCII ID。插入笔记时排序所有已加载页面；缓存更新和列表展示共用同一排序器，防止续页再次把已编辑笔记放错位置。当前缀笔记因改名、更新时间回退或 ID 映射移出前缀时，通过有条件的 offset 重叠防止遗漏源记录；反复编辑已在前缀外的笔记不会持续回退。未新增输入限制、代理/重试/fallback、立即读取、迁移或依赖。
- **27 项**缓存/运行时相关测试全部通过，以实际 sidecar ORDER BY 在 SQLite 中执行的结果为准。本轮发现对应的回归用例在相应修复前均已暴露问题。覆盖双向排序、标题回退/NUL/Unicode、同名更新时间与 ID 次序、插入、映射、活动缓存更新不调用查询函数，以及修正游标后继续加载直至完整源记录。最终 Web 类型检查和桌面 Web 构建通过；基于当前上游 `main` 的独立 PR 分支也通过了 Web/移动端类型检查及桌面 Web 构建。
- 原有 A–Z/Z–A 正文编辑、改名及 120 条笔记跨页证据对原输入仍有效。另用 Electron 44.7 和未修改的官方 sidecar 运行最终 macOS 原生候选，验证本轮发现的路径：将首页笔记改名到接近末尾后继续滚动，最终完整显示 **123 / 123** 条测试笔记，不再漏掉源记录；见[最终分页截图](evidence/2026-11-01-memo-sort-after-save/fixed-cursor-after-next-page.png)。所有操作均在隔离的本地测试实例中完成，未操作用户 Cloudflare 数据。
- 最终本地微基准包含缓存更新及已加载列表的 Map/展示投影，使用 20% 同名标题、递增的保存时间、每页 50 条、预热 10 次、计时 100 次。5,000 条已加载摘要的正文更新/展示处理中位耗时 **6.704 → 1.101 ms**，新笔记插入/展示为 **2.977 ms**。结果不含 React 绘制、原生/数据库/网络工作，也不是生产延迟；完整系列见[性能证据](evidence/2026-11-01-memo-sort-after-save/performance.json)。普通正文保存不增加游标工作或读取；移出前缀只让下一次正常分页产生有界重叠，不立即读取或逐页全库扫描。
- 最终受影响路径的正确性、简化和设计适配性审查无范围内待处理的实质问题。缓存和展示共用比较实现，未增加另一套排序算法或数据来源。产品 diff 仅涉及 `memo-list-cache.ts` 及 `WorkspaceApp.tsx` 的桌面标题列表投影，测试/文档/证据验证对应行为；分享和备份行为保持不变。Release/安装器验证不属于此次源码改动，Windows 专属界面验证待具备对应环境后完成。
