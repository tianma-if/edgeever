# Third-party note import change scope

[简体中文](2026-10-27-third-party-import.zh-CN.md)

Related: [Issue #657](https://github.com/tianma-if/edgeever/issues/657). Contract: [third-party import plan](../third-party-import-plan.md).

## Problem and objective

Extend the former Evernote command-line guide entry with online, additive Web/desktop imports from Evernote, Obsidian and Joplin, preserving hierarchy, metadata, images and attachments. Preflight precedes writes; retries within a task reuse its created objects, while separate imports do not automatically merge existing data.

## Unchanged boundaries

- Preserve MCP imports, ordinary editing, offline queues, Rust structures, sync, backup and encrypted restore contracts. Apart from R28/R39's paging-index migrations, add no database structures, global required settings or authorization scopes.
- No native mobile import entry, cross-run merging, resume after exiting the app, Obsidian plugin/inter-note conversion, remote-image capture or whole-library transaction rollback.
- Keep installers, automatic updates, versions and release/deployment mechanisms unchanged. Existing Cloudflare upgrades retain the Worker, D1, R2, administrator and authentication Secret without resetting passwords or replacing the instance. Tests use authored sources and isolated directories, never personal libraries.

## Important choices and evolution

Parse on the client and write through the shared API rather than adding a desktop offline-import protocol. This gives Web and Electron one behavior and Cloudflare and Docker one business implementation without extending Rust or sync protocols. Indexes contain locators and metadata; bodies and resources are read per note. Results retain only locators, version baselines and resource mappings rather than accumulating the library's bodies again.

The original rejection of more than 24 tags is superseded by I07/R11: normalize in source order, keep the first 24, ignore extras and warn. This retains the existing API storage boundary without blocking a library migration over surplus tags. Missing Joplin ancestors are export boundaries rather than invented folders; included cycles and invalid parent types remain errors.

Use mature Markdown parsers and serializers rather than global regex replacement or a dual-parser adapter. Optional image-link attributes fit the existing block-image schema; structural empty list paragraphs are handled only in the export projection, not by changing storage. Dependency choices follow the lockfile and actual TipTap contract, not drift in a local dependency directory.

## Large-library reads and exports

Per-note creation previously called `getNotebook` with repeated `COUNT/MAX`, producing `N × (N−1)` cumulative memo-row aggregate contributions for N notes in one folder. Web exports also rescanned and sorted successive OFFSET pages. R27 uses lightweight existence checks; R28 gives updated clients indexed continuation while retaining legacy fields, ordering, OFFSET calls and backup consistency.

## Risks and rollback

Import is high-risk data writing: partial new objects, duplicates, incorrect timestamps and resource references are the worst outcomes. Append only, retain sources, item outcomes and commit baselines; cancellation does not undo completed writes and code rollback does not delete imported notes. Removing the entry/routes leaves imported data usable as ordinary notes. Cleanup requires confirmed actual IDs, never bulk deletion by name.

Shared codec repairs affect editing round-trips for images, lists and attachment labels. Use source Markdown, original JSON and independent resource bytes as expectations; do not rewrite historical notes automatically. Before deployment, retain the Worker version, private D1 backup and an independent recovery entry. Stop later deployment steps if migrations or key acceptance fail and restore from these materials as needed.
