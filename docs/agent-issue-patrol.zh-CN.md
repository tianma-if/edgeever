# Issue 巡检执行细则

通用规则见 [变更风险评估](../AGENTS.md#变更风险评估)、[GitHub 协作](../AGENTS.md#github-协作)和[巡检共用约定](../AGENTS.md#巡检共用约定)。

## 巡检范围

- 首次检查最近 24 小时新增或更新的 Issue。之后从上次成功扫描位置继续，并主动复查未结项。有可执行的下一步就当轮推进，无需等待新评论。上轮因工作区只读而暂停的修复，在恢复可写后继续。
- 已有 PR 覆盖某个问题时，将该问题交给 [PR 巡检](agent-pr-review.zh-CN.md)。同一 Issue 的其他问题继续跟进。

## 处理规则

- 同一 Issue 含多项反馈时，逐项判断和推进。
- 已确认的低风险产品缺陷默认当轮自动修复，无需另外确认。改代码前在巡检状态中记录 Issue 编号、起始提交和计划修改的文件。验证通过后当轮提交并推送，在提交说明中写 `Refs #<编号>`，避开自动关闭关键词。确认远端已包含该提交后，才记为已推送，并在 Issue 回复提交链接、验证结果和发布状态。
- 每轮收尾核对本轮修复是否仍有未提交改动、未推送提交或待发回复。未完成时记录已做到哪一步、涉及文件或提交、阻塞原因及下一步，并在巡检汇报中明确说明；下轮先核对本地和远端实际状态，再接着处理。恢复前须确认遗留改动属于巡检，遇归属不明或用户改动时按只读规则处理。已推送提交若遗漏 Issue 编号，在 Issue 评论补上提交链接。
- 证据不足时先完成可做的复现和验证，缺少外部信息时记录所需证据。确认缺陷后重新分级。高风险改动或仍无法充分验证的改动，等维护者审阅方案后再改。
- 值得做的功能建议给一份方案，实现和排期由维护者决定。
- 逐条发送并核对 GitHub 返回的评论 ID，拿到回执才记为已发。一条失败不阻断其他 Issue。收尾时核对本轮应发回复；遇发送报错先查评论是否已落地，确认未发且当轮可恢复就重试，其余记入待办并在巡检汇报中列出。

## 状态记录

`issues.json` 分别记录提交、推送和回复进度，保存已读更新时间和评论 ID、分类、关联 PR、待办、修复提交、验证结果和已发回复 ID。混合反馈在同一个 Issue 条目内按子项记录分类、进度、验证结果、下一步和等待条件。
