# 第三方笔记导入实现方案

[English](third-party-import-plan.md)

关联：[Issue #657](https://github.com/tianma-if/edgeever/issues/657)。第 1–8 节为已实现契约；第 9 节为已实施的 D1 优化范围与验收。[验收范围与结论](changes/evidence/2026-10-27-third-party-import/README.zh-CN.md)。

## 1. 实现方向与首版边界

在“设置 → 导入导出”新增统一的“从其他应用导入”入口。三种来源共用文件读取、预检、目标目录选择、执行和结果界面，各自负责解析来源格式。用户无需配置 MCP、API Key 或命令行。

首版覆盖 **Web 与 Electron 桌面端，联网导入到当前实例、当前账号**。本地扫描不依赖网络，确认写入时需要连接实例。桌面端在写入阶段暂停后台同步，结束后恢复并拉取结果。Android 和 iOS 继续通过现有同步读取导入结果，本期不增加原生文件导入入口。

导入使用追加语义：新建源目录和笔记，不按名称合并、覆盖既有内容。指定父笔记本只改变新增目录的挂载位置，不修改父笔记本。一次新的导入创建一批新数据；同一任务内的重试复用已创建的笔记，不提供跨次自动合并或关闭应用后的断点续传。

三种来源及 Issue 要求的文件、目录和压缩包形式都保留在首版，不以分步开发缩减最终交付范围。

## 2. 复用与架构选择

| 位置 | 可复用能力 | 接入方式 |
| --- | --- | --- |
| `apps/web/src/components/SettingsPane.tsx` | Web 使用 `DataExportCard`，桌面使用 `DesktopScheduledBackupCard` | 保留两个备份入口，以第三方导入卡替换指南卡，卡内保留指南链接 |
| `packages/shared/src/backup-archive.ts` | 使用 `@zip.js/zip.js` 2.24.0，支持 ZIP64、按条目读取与流式恢复 | 复用依赖及读取方式，不要求第三方 ZIP 携带 EdgeEver manifest，不改备份格式 |
| `apps/api/src/memo-service.ts::importMemosRecord` | 每批 1–25 篇、逐项结果、时间戳导入、`source + externalId` 幂等；通过数据库适配层写入 | 增加薄 REST 入口复用该服务，不另写一套创建笔记逻辑，不改变 MCP 的既有语义 |
| `packages/client/src/index.ts` | 普通创建可传时间戳；资源支持分片上传；正文更新需要编辑会话与版本保护 | 增加导入方法，并为 `updateMemo` 类型补齐服务端已支持的可选时间字段 |
| `apps/web/src/lib/desktop-sync.ts` | `pauseDesktopSyncForImport()` 等待在途同步并返回释放函数 | 在确认写入后持有，所有退出路径释放；先释放，再刷新工作区 |
| `crates/desktop-sidecar/src/memo.rs::create_memo` | 普通本地创建依赖数据库生成时间，不读取导入时间字段 | 不把本次导入接到普通本地创建，避免扩展 Rust 存储和离线队列协议 |
| `scripts/import-evernote-enex-via-mcp.mjs` | 已有 ENML 转换、附件关联和元数据映射 | 参考格式规则；不沿用整文件读取、仅取末级父目录、400,000 字符截断及自动压图 |

因此，采用**客户端解析、共用服务端写入**，而不是让 Web、桌面各实现一套离线导入。Cloudflare 与 Docker 继续执行相同的 API 业务代码，原始归档不整包上传到服务器。

## 3. 输入、元数据与链接规则

### Evernote / 印象笔记

- 接受单个或多个 `.enex`、包含 ENEX 的多级目录，以及这些内容的 ZIP。目录路径完整保留，每个 ENEX 文件名对应一个叶级笔记本；多选且没有相对路径的文件作为同级笔记本。不推测导出中不存在的原平台目录。
- `.notes` 明确提示“请从印象笔记导出为 .enex 后重试”，不作为 XML 或 ZIP 猜测解析。
- 分块扫描 XML，读取标题、标签、`created`、`updated`、ENML 和内嵌资源描述。导入时逐篇处理，资源 base64 分块解码；不能在 SAX 的单个文本事件里重新积累整个附件。
- ENML 转换沿用 Turndown，覆盖表格、待办、图片和附件。链接中的图片保持行内结构，保留外层 URL/title；普通媒体仍沿用既有块布局。MD5 只用于匹配 ENEX 的 `en-media` 资源标识，采用增量实现；不把它当作安全校验。
- 笔记自带但未在正文中引用的附件仍上传，并在正文末尾补充附件链接。加密段落以纯文本保留原始加密内容及提示，不用占位文案替换后丢弃原文。

### Obsidian Vault

- 接受目录或 ZIP，按 Markdown 所在路径还原目录；忽略 `.obsidian`、`.git`、`.trash` 及系统索引文件，不执行插件或脚本。
- 复用 Front Matter 读取能力，映射有效的 `title`、`tags`；导入解析器增加 `created` / `createdAt`、`updated` / `updatedAt` 时间映射，保留其他属性与原始 Front Matter。两个同义字段冲突时预检列出冲突，不任取一个。
- 处理标准 Markdown 本地图片/附件和 `![[图片或附件]]`。路径按 Vault 规则解析，包括中文、空格、相对路径和根相对路径；仅能在所选 Vault 中解析。重名且无法唯一定位时列出问题，不猜测。[Obsidian 链接规则](https://obsidian.md/help/links)
- 本次不转换笔记间双链、块引用、笔记嵌入、Canvas 或 Dataview；保留来源文本，对无法继续使用的引用给出预检提示。图片/附件嵌入属于必须完成的资源迁移，不归入这些排除项。

### Joplin

- 明确支持 RAW 导出目录、Markdown 导出目录（含有/无 Front Matter 两种）及其 ZIP，另支持 `.jex`。按条目结构识别，而不是仅按扩展名识别。
- JEX 是 TAR；RAW 是相同数据的目录形式。读取笔记本父子关系、笔记、标签关联及资源记录，再处理正文中的资源 ID 引用；不能把每个 `.md` 条目都当作用户笔记。[Joplin 导出说明](https://joplinapp.org/help/apps/import_export/#exporting)
- 资源目录或 32 位文件名只表示资源候选；Markdown 须由另一个源条目的有效 RAW 资源描述确认后才按附件跳过全文读取，未确认的 Markdown 仍可作为笔记。
- Markdown 导出按路径和存在的元数据处理。源文件没有导出的时间和标签无法还原，预检必须区分“来源未提供”和“解析失败”。

### 共用规则

- 有效来源时间保留其时刻，写入为带时区的 ISO 时间。缺失或无法确定时区的时间保留原始值并提示；不冒充原始笔记时间，缺失字段沿用现有创建接口的导入时刻默认值。
- `_resources`、`assets` 等目录是否建笔记本取决于是否包含笔记或其子目录是否含笔记，不能只按名称整目录排除。纯资源目录不建空笔记本。
- 同一附件在同一篇笔记中被多次引用只上传一次；跨笔记沿用现有资源归属模型分别上传。预检的“附件数”指计划创建的 EdgeEver 资源数，不是唯一源文件数；未关联到任何笔记的资源列为未导入项。
- 只改写正文中实际的图片/链接目标，不对代码块、行内代码或相似文字做全局替换。
- 标准 Markdown 中的外部 URI（如 HTTP(S)、FTP、Obsidian 应用链接）原文保留，不作为本地附件查找，不读取目标，也不新增预检警告。既有链接打开和渲染安全策略不变。
- 路径规范化后不得越出所选根目录；`file:` URI 和 Windows 盘符形式（含驱动器相对路径）继续按本地路径规则拒绝，Wiki 目标仍按字面文件名处理。不跟随归档中的符号链接，不把归档解压到用户任意目录。同一规范路径对应多个条目时报告歧义。
- HTML 仅转换静态内容，不执行脚本或事件处理器；XML 不联网读取 DTD 或解析外部实体，正常 ENEX 的格式声明仍可读取。
- 沿用当前名称、标题和上传限制，包括笔记本名 80 字符、标题 160 字符、图片 100 MiB、其他附件 1 GiB。标签按来源顺序去空、去重后保留前 24 个；超出部分忽略，预检提示忽略数量但不阻止导入。普通编辑的标签保存规则不变。预检列出不符合项，不截断正文、标题或自动压图来“导入成功”。影响完整还原的错误须先修正，缺失可选元数据等警告可确认后继续。

## 4. 模块与内存模型

新增 `packages/shared/src/note-import/`，保存平台无关的来源描述、目录计划、解析器、引用解析和结果类型。按子路径导出，不从共享包总入口拉入解析依赖。模块职责如下：

- `types.ts`：`ImportFile`、`ImportNote`、`ImportSummary`、资源描述和分阶段结果。
- `sources.ts`：目录、ZIP、TAR 的统一读取接口，返回条目元数据及按需打开的字节流。
- `session.ts`、`metadata.ts`：来源格式扫描、目录/资源映射、元数据及逐篇读取；`evernote.ts` 专门处理流式 ENEX。ENML 转换通过注入的转换函数完成，不让 Worker 依赖 DOM。
- `references.ts`：解析实际图片/链接位置并精确改写目标 URL。

Web 端新增 `apps/web/src/lib/note-import/` 负责文件选择、Web Worker、临时存储、执行器与任务状态；Web 和 Electron 渲染器共用它。使用目录输入和文件输入保留相对路径，不为首版新增接受任意路径的 Electron IPC。

任务索引只记录导入 ID、来源类型、目录、笔记元数据、资源描述、问题清单及读取定位，不保存全库正文或附件 base64。大索引按页存入任务级 IndexedDB，界面按页读取预览。已完成结果只保存笔记位置、版本、时间及资源映射；仅当前未完成项保留核对提交所需的目标正文。

扫描与解压在 Worker 执行。ZIP 沿用 `@zip.js/zip.js`；XML 首选 `sax`，TAR 首选基于异步迭代器的 `it-tar`，实施时先验证浏览器构建和大字段行为，再锁定版本与许可证。不采用已归档的 `saxes`，不自行实现 XML/TAR 编解码。[SAX](https://github.com/isaacs/sax-js) · [it-tar](https://github.com/alanshaw/it-tar)

ENEX 第一遍只扫描元数据和资源大小，确认后第二遍按文件顺序处理，避免为每篇笔记重新扫描整个 ENEX。ZIP/TAR 读取遵守背压，不一次解压全部条目。单篇所需的解码资源按块暂存到应用私有存储，并接入已有 `uploadMemoResourceParts` 的 `readPart` 接口；DOM 转换逐篇执行并让出事件循环。

同时只处理一篇笔记的正文和附件，完成后释放其字节。临时空间不足时明确停止，不能降级成全量内存缓存。完成或取消后清理解码资源块；未完成结果的必要索引和 ID 映射保留到结果关闭，以便当前任务重试时按需重读来源文件。打开结果笔记仅隐藏弹窗、保留当前任务以供重试；显式关闭结果或改选来源才清理任务索引。不触碰源目录。

## 5. 写入流程与错误处理

### 接口增量

在 `apps/api/src/import-routes.ts` 增加：

- `GET /api/v1/imports/capabilities`：返回协议版本及现有批次上限；开始写入前检测支持情况。旧服务端不支持时仅提示升级服务端，原编辑、同步和备份功能保持可用。
- `POST /api/v1/imports/memos`：接受 `importId`、来源类型、目标笔记本、条目和 `dryRun`，校验后调用现有 `importMemosRecord`。由服务端构造 `third-party-<format>-<importId>` 来源标识；每篇使用预检时固定的条目 ID，符合既有 80/512 字符来源键限制。返回逐项创建、跳过和失败结果。

沿用会话认证、工作区隔离及笔记读写权限，不要求客户端生成 MCP Token，不新增授权范围。普通笔记本创建、附件上传、编辑会话和正文更新继续使用现有 API。`packages/client/src/index.ts` 增加对应方法及可选 `createdAt` / `updatedAt` 更新字段，既有调用不新增必填参数。导入不需要持久化任务表；配套大库导出修复新增 `0085` 笔记索引，见[变更清单](changes/2026-10-27-third-party-import.zh-CN.md#大库读取与导出)。

### 执行顺序

1. 选择来源类型和文件，扫描完成后显示目标实例/账号、计划新增的笔记本/笔记/附件数、目录树及问题；扫描和取消预检都不写远端。
2. 用户选择“创建为顶层笔记本”或已有父笔记本。目标从服务端目录读取，本地尚未同步的父笔记本需正常同步后才能选择。显示实际将新增的树，不额外强加来源包装层；确认前不创建笔记本。
3. 确认时固定实例、账号、工作区、目标和请求上下文；检查新 API 可用。桌面取得同步暂停句柄并等待在途同步结束，随后按父子顺序调用现有 API 创建目录，每个目录创建前先持久化待确认标记，再保存源目录到目标 ID 的映射；服务端已创建但本地映射保存失败时保持待确认，不盲目重复创建。
4. 按目标笔记本逐篇创建笔记，每次 1 篇，沿用服务端既有 1–25 篇批次契约，不新增限制；完成下一步后再处理下一篇。保留来源正文和时间，记录返回的真实 ID、`revision` 和 `contentHash` 作为导入基线；`skipped` 只代表该项已创建，不代表附件和最终正文已经完成。
5. 逐篇上传附件，保存源资源到远端 URL 的映射。全部必要附件就绪后取得编辑会话，先核对当前版本和内容仍匹配该任务保存的导入基线，再受保护地提交改写正文，同时带回来源或首次创建时的时间戳。取得新会话不能用于接纳并覆盖中途人工编辑；不匹配即报告冲突。上传和改写不能把原修改时间变成迁移时间，成功提交后更新任务基线。
6. 只有正文、所需附件和最终提交都完成才计为成功。最后释放桌面暂停句柄，再调用工作区刷新；刷新在暂停期间会被现有同步函数跳过，不能颠倒顺序。导入已完成但本地拉取失败时分别显示“已导入”“同步待重试”，不重新导入。

### 失败、取消与重试

- 单篇附件或最终提交失败时保留已写入的笔记及任务内映射，标为未完成，允许当前任务重试；重试只补缺失步骤，不再创建另一篇。结果列出可打开的未完成笔记与具体失败附件，不能只显示总成功数。
- 不增加整批 POST、目录创建或最终正文更新的盲重试。笔记创建结果不明时可用同一导入键查明/重放；目录创建或附件提交结果不明且无法确认归属时停止该步骤并报告，不假定失败、再次创建。
- 分片 PUT 及其重试沿用现有上传客户端。新任务不扫描既有知识库按标题猜测重复，不将一次新导入伪装为上次任务续传。
- 取消停止新写入并终止可取消的读取/上传，保留已完成结果和明确列出的未完成项；不自动删除既有数据，也不承诺整库事务回滚。请求已提交但响应未收到的项目单独显示“结果待确认”。
- 退出登录、切换账号或实例时取消旧任务，迟到结果不能更新新工作区。当前工作区一次运行一个前台导入任务，状态由工作区级控制器持有，不随设置卡片卸载而丢失；完全退出应用后不继续执行。
- 所有终止路径在 `finally` 中释放同步暂停。已有本地待同步编辑保持原队列，不为导入清空、覆盖或强行迁移它们。

## 6. 界面只展示完成操作所需内容

新建 `ThirdPartyImportCard` 和共用 `ThirdPartyImportDialog`，复用 shadcn/ui 的 Dialog、选择器、进度和 Tooltip。入口只显示来源选择、选择文件/文件夹与迁移指南链接。

预检弹窗的重点是三个数量、目标位置和目录树；警告在对应文件/笔记旁展开，影响导入的错误集中可定位。执行期间展示当前阶段、当前文件及已完成/总数，扫描总量未知时不伪造百分比。结果区分成功、未完成、取消和待确认，并提供打开目标目录及重试失败步骤。

导入文案更新项目现有语言目录，不改变设置页其他分组、备份/加密恢复、单文件 Markdown 拖入和原命令行指南的使用方式。

## 7. 验收

关键验收围绕实际流程：

- 每种来源均从设置入口操作，预检数量与实际新增数据一致；取消预检后数据库和资源存储无新增。使用合法的脱敏导出或自行创建的真实导出，不使用个人知识库。
- 在 Cloudflare 本地 D1/R2 与 Docker SQLite/对象存储适配器上跑同一组核心流程，读回完整路径、标题、标签、创建/修改时间和资源关联。先在当前版本实例创建既有数据，再升级到新增 API 版本并导入，确认既有数据及旧编辑/备份入口仍按原契约工作。
- 关闭源目录访问后重开导入笔记，图片和附件从 EdgeEver 资源地址读取；校验实际内容与引用位置，而不只确认 HTTP 200。旧指南和 EdgeEver ZIP v1/v2、桌面加密恢复相关未改行为复用仍适用的既有证据。
- 构造首篇成功、第二篇附件失败、第三篇未开始的流程，确认结果准确；同一任务重试不重复第一篇或第二篇；编辑冲突不覆盖人工修改。桌面成功、失败、取消后同步都能恢复，刷新后的本地时间与服务端一致。
- 固定笔记数量与正文规模，分别导入总附件约 1 GiB 和 4 GiB 的多附件归档，各单文件保持现有上传限制内。记录浏览器/桌面版本、峰值 heap/RSS、活动缓冲与临时磁盘占用；确认内存不随总附件体积近似同比增长，界面可取消、无整包内存副本。单个大 ENEX base64 字段另外覆盖，不能只验证由很多小文件组成的 Vault。
- 增长笔记数量，对比真实 Worker/IndexedDB 的预检表现，并通过真实 API 导入多篇大正文。结果分页只保留基线，不含完整 Markdown/JSON/摘要；同任务重试及人工编辑冲突保护仍成立。
- 覆盖 `.notes`、缺附件、重名引用、目录越界、纯资源目录、缺失元数据及现有限制，检查提示和最终计数。无法通过端到端有效区分的解析细节再补隔离测试。

必要检查为 `bun run typecheck`、`bun run typecheck:mobile`、`bun run build:web` 及受影响的实际流程。若后续扩大到 Android，必须使用 USB 真机验收。

## 8. 风险、回退与待验证项

这是高风险的数据写入功能。最坏结果是部分目录/笔记已创建但附件未完成、重复导入，或时间/链接转换错误；因此只向新建对象写入、保留源文件、记录逐项结果、不覆盖既有笔记，并用编辑会话保护最终提交。导入过程中工作区备份版本会按既有机制变化，自动备份可能因数据变化重试；不为此修改备份调度或放宽一致性校验。

功能回退可移除新增入口和 REST 路由，旧编辑、同步、备份协议不变；已导入数据仍按普通笔记可用。代码回退不会撤销已写入数据。需要清理结果时按本次记录的实际 ID 人工确认，不按名称批量删除。

[验收结论](changes/evidence/2026-10-27-third-party-import/README.zh-CN.md)区分当前 Web/API 候选、此前 macOS/Linux 原生流程、Cloudflare 旧实例升级和大库测量。Evernote 11.40.2 原始 ENEX、Obsidian 1.14.5 Vault 及 Joplin 3.7.21 RAW/JEX/两种 Markdown 导出均按声明保留正文、层级、原始时间及资源字节。

R27–R30 和 `0085` 索引已部署到既有 Cloudflare 实例。R31–R39 和 `0086` 已在本地验证、尚未部署；此前原生验收未覆盖最新修复。Windows 原生、移动端真机、旧客户端编辑、AppImage 安装/跨版本升级及 Docker 容器部署仍未验证。最近一次 Cloudflare 验收未覆盖密码重新登录和 Web ZIP 本机保存，接受该次部署时需通过对应入口检查。

## 9. D1 额度优化

### 先补分页索引

本轮只为笔记增加 `(workspace_id, id)` 索引，覆盖一致性备份的笔记分页和首次同步。收益最大，且不需要改 API、客户端或备份协议。无变更备份探测和搜索索引去重作为后续独立优化，不一起改动成熟链路。

当前两个入口均按 `id` 续页，但缺少匹配工作区和 ID 范围的索引。本地 D1 的备份查询选择创建时间索引的工作区前缀，首次同步选择归档索引的工作区前缀，然后重复扫描、排序。此前 SQLite VM 测量不能代替这一环境的 D1 行数，相关结论以[原生行数对照](changes/evidence/2026-10-27-third-party-import/README.zh-CN.md#d1-原生行数对照)补充。

4,047 篇笔记的隔离对照中，仅添加候选索引，完整备份读取从 1,356,449 行降至 50,073 行，首次同步从 195,818 行降至 24,412 行；完整返回数据和顺序一致。这些是本地 workerd D1 的 `meta.rows_read`，尚未完成线上同规模验证。

### 实现范围与选择

新增递增 migration `0086_memo_id_paging_index.sql`，只包含：

```sql
CREATE INDEX idx_memos_workspace_id ON memos(workspace_id, id);
```

- 保留已执行的 `0085` 及其创建时间索引：Web JSON/Markdown 导出仍按创建时间、ID 排序。
- 选择 `(workspace_id, id)` 而非 `(workspace_id, is_deleted, id)`：首次同步需要包含已删除笔记，不约束 `is_deleted`；后者不能让两个入口共用连续的 ID 范围查找。备份继续按原条件过滤已删除笔记。
- 保持现有查询、游标、分页大小、响应字段与顺序；Cloudflare D1 和自托管 SQLite 共用同一 migration。旧客户端无需新增参数。
- 不强制 `INDEXED BY`，也不以定期 `ANALYZE` 代替缺失索引；避免依赖另一种不匹配顺序或变化中的统计信息。
- 不增加导入上限、额度配置、自动重试、调度延迟或降级读取，不删幂等记录、审计或并发保护。

### 读写成本与风险

上述数据的候选索引构建读取 8,203 行、写入 4,048 行，数据库大小增加 224 KiB。正式迁移的创建服务对照由 25 行写入增至 26 行，普通正文更新前后同为 26 行；删除或改变工作区/ID 时也需要维护索引。导入写预算仍需计入原有标签、资源、审计及新增索引维护。

这是高风险存储迁移。主要风险是构建期间的数据库排队、空间或当日读写余量不足，以及其他查询选择新索引后退化。实施前记录数据库大小与读写余量；迁移失败时停止后续部署步骤。迁移只增加索引，不重写业务字段或触发器。

### 验收与回退

1. 复用 `backup-consistency.test.mjs` 的完整 Schema 夹具，在同一工作区上下文验证备份与同步路由；旧结构复现分页主查询重复扫描/排序，再应用新 migration。既有 `sync-routes.test.mjs` 继续检查同步合同。不要预先执行 `ANALYZE` 掩盖问题。
2. 验证旧结构和存量数据升级后，完整备份、首次同步及旧客户端默认调用的笔记、目录、正文、标签、时间、资源元数据、修订与顺序一致。覆盖交错 ID 的多个工作区、已删除笔记和跨页边界；权限、一致性版本检查及来源变更时的拒绝行为保持原样。
3. 复用当前有效的 4,047 篇隔离对照；对最终 migration 的受影响部分补验。新增规模回归比较固定内容的 1,000/4,000 篇：笔记分页累计读量应近似线性，四倍笔记不超过五倍读取；查询计划应直接按工作区和 ID 范围定位，而非每页重扫。只检查分页主查询，不能把既有回退子查询的排序误判为分页退化。按实际 `rows_read` / `rows_written` 计量，同时确认新写入和创建时间导出未退化。
4. 实际部署验收区分旧实例迁移、API 数据读回与 D1 用量观察。当前本地旧结构升级、接口契约和正式 migration 的规模/写入成本检查通过；部署后的索引构建成本、计划和完整流程读量仍需记录。未变化的原生归档兼容证据继续复用。

应用回退不会自动移除索引。若索引引起退化，新增后续 migration 删除该索引，保留业务数据；不修改已执行 migration，不删除已有创建时间索引。部署前保留旧 Worker 版本、数据库备份及独立恢复入口。
